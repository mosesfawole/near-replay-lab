# RunReport 1.0.0

The shared source of truth is `packages/core/src/types.ts`. Import types and `validateRunReport`, `assertRunReport`, and `evaluateTargetEvidence` from `packages/core/src/index.ts`. The core has no Node or signing dependency and can be imported by the read-only dashboard. Unsupported schema versions are rejected.

All amounts and nonces at JSON boundaries are exact base-10 integer strings. Account balances, deposits, approval amounts, receipt-derived credit, and observed credit never use floating point. `observedCreditYocto` can be negative; other amounts are unsigned. Block heights are safe integer numbers. Times are ISO timestamps.

The report contains:

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Exactly `"1.0.0"`. |
| `runId`, `createdAt` | Local run identifier and capture time. |
| `network` | `{ networkId: "testnet", rpcUrl }`; the configured native NEAR testnet RPC. The runnable default is `https://test.rpc.fastnear.com`, listed in [NEAR's provider documentation](https://docs.near.org/api/rpc/providers). Captures retain the URL actually used. |
| `provenance` | `{ mode: "live" \| "recorded" \| "synthetic", description }`. Live means the local runner captured RPC evidence; recorded means a saved capture; synthetic means an offline fixture. The label is explicit and is not a cryptographic proof of origin. |
| `versions` | `{ adapter, build }`, initially `near-api-js@7.4.0` and `0.1.0`. |
| `scenarios` | Nonempty `ScenarioReport[]`. Each scenario has `scenarioId`, `title`, `kind`, `description`, `approval`, and nonempty `targets`. IDs are unique within their containing collection. |
| `rpcEvidence` | Every public RPC record, including network verification, access-key queries, failed requests and block queries that occur before or outside an attempt. |

`ApprovalDetails` records `approvalId`, `signerId`, `recipientId`, `amountYocto`, `source`, and `approvedAt`, with optional `expiresAt`, `invoiceId`, and `evidence`. Sources are `operator-config`, `constructed-fixture`, or `on-chain`. An operator-config approval describes the local requested transfer; it is not an on-chain approval. Fixture approvals and attack construction must be labeled in the scenario description.

`TargetReport` contains `targetId`, `label`, `targetKind` (`direct`, `unsafe`, or `guarded`), `accountId`, `attempts`, `snapshots`, and `verdict`. Optional `approval` overrides the scenario approval for that target; fixture comparisons need this because each fixture has its own dedicated recipients and fresh invoice. Consumers and evaluators use `target.approval ?? scenario.approval`. Optional `errors` holds unresolved local or capture failures; optional `stateSnapshots` holds finalized public contract views. `accountId` is the signer for the direct target and the fixture account for contract targets.

`snapshots` is `{ before: RecipientSnapshot | null, after: RecipientSnapshot | null, relatedAccounts?: Record<accountId, BalanceSnapshots> }`. The first before/after pair observes the canonical approved recipient. Related accounts can hold the substituted recipient and other dedicated accounts. Each snapshot has `recipientId`, `amountYocto`, `lockedYocto`, `queriedAt`, `block`, and complete query `evidence`. Nullable snapshots let a failed run remain a valid honest report.

`TransactionAttempt` has `attemptId`, `actionKind`, `signerId`, `publicKey`, `receiverId`, `amountYocto`, `nonce`, locally computed `txHash`, `signedAt`, and public `actions`. It also has nullable `broadcast`, `observations: RpcEvidence[]`, nullable `finalOutcome`, and `finalBlocks: FinalBlockReference[]`. Fixture targets retain the owner `approve` attempt alongside worker `pay` attempts; function-call attached deposits are `"0"`, and native credit comes from downstream receipts. Only unresolved errors belong in optional `error`. A transport failure that is later resolved by a complete FINAL observation remains visible in the broadcast record without becoming a permanent unknown outcome. The constructed discard keeps `response: null` and `INJECTED_RESPONSE_DISCARD` in the broadcast record. Signed bytes and private keys have no report field.

`FinalBlockReference` is `{ hash, height, finality: "FINAL", evidence? }`. Finalized transaction and receipt block hashes come from the complete FINAL outcome; their heights are queried by block hash. An after balance must cover every final outcome block. A direct before balance precedes its transfer; fixture before balances precede every `pay` execution and can follow the finalized owner approval.

`RpcEvidence` is `{ method, params, requestedAt, receivedAt, response: JsonValue | null, error? }`. `response` preserves the complete public JSON-RPC envelope, including `result` or `error`. A transport failure uses `response: null` and a public error. For `send_tx`, only public request metadata is saved and `signed_tx_base64` is omitted; the signed hash and action details are retained on the attempt. A `PublicError` has `category`, `message`, and optional `code`; categories are `configuration`, `transport`, `timeout`, `rpc`, `evidence`, or `local`.

The transport uses the official SDK provider methods and signer with bounded requests: default RPC timeout 15 seconds, FINAL observation and finalized-balance/view deadlines 90 seconds, and polling interval 1 second. `send_tx` uses `wait_until: "INCLUDED"`; its response may contain no hash. The runner saves `baseEncode(txHash)` from the official signer before broadcasting. A definitive `INVALID_TRANSACTION` retains the complete raw error envelope in `broadcast.response`, keeps the terminal public error in both the broadcast and attempt, and skips FINAL polling. Allowance or gas validation rejection stays INCONCLUSIVE; it cannot establish contract protection. Direct observation first uses the SDK `viewTransactionStatus` (`tx`), then method-not-found fallbacks to `tx_status` and `EXPERIMENTAL_tx_status`. Function calls first use `viewTransactionStatusWithReceipts` (`EXPERIMENTAL_tx_status`), then `tx_status`; a FINAL response missing receipt bodies also attempts that fallback and retains an explicit incomplete-evidence error if bodies remain missing. All observations use the saved hash, sender and `wait_until: "FINAL"`. No fallback rebroadcasts or re-signs a transaction. An access-key nonce returned as an unsafe JavaScript integer is refused rather than approximated. Suite signing uses explicit per-key nonce floors; only independent-key concurrency broadcasts overlap, and status observations stay serial.

The finalized-expiry wait shares one deadline across its current-block lookup, historical block verification and polling. Each request caps its fetch/body-read budget to the remaining time, passes an abort signal and rejects late results before accepting a reached timestamp. A legacy NEAR query can place a string `error` inside the outer RPC `result`; that complete envelope remains public evidence while the transport throws a typed RPC failure. `UNKNOWN_ACCESS_KEY` is assigned only to the exact missing-key message for the requested key under `view_access_key`, with a nonempty block hash and safe nonnegative block height. Other malformed, empty, permission or mismatched-key legacy errors use `LEGACY_QUERY_ERROR`. Application JSON encoded inside successful call-function bytes is unaffected.

`TargetVerdict` has `status` (`HOLDS`, `VIOLATED`, or `INCONCLUSIVE`), `summary`, `reasonCodes`, `intendedCreditYocto`, nullable `observedCreditYocto`, nullable `successfulReceiptCreditYocto`, and deduplicated `transactionHashes`.

The direct evaluator remains compatible with the original legitimate transfer reports. HOLDS requires a complete FINAL outcome, linked successful transfer receipts, transaction identity/action consistency, finalized before/after balances for the approved recipient, and agreement between receipt-derived credit and the exact balance delta. Every `SuccessReceiptId` must reference a present child outcome and terminate in success; missing links and cycles remain INCONCLUSIVE. The transaction's terminal value must match the top-level successful final status. One exact intended credit establishes HOLDS. Proven wrong recipient, wrong amount or multiple distinct successful credits establishes VIOLATED. Empty, missing, nonfinal, nonce-failed, transport-unknown or inconsistent evidence is INCONCLUSIVE. An unrelated balance change is INCONCLUSIVE; it is not attributed to the tested payment. Rebroadcasts of one identical signed transaction count once, including semantically equal outcomes whose object keys are reordered.

The claimed final outcome must match a successful raw FINAL status response for the retained hash and signer. Each final transaction/receipt block reference must match its raw `block` response header. Structured summaries alone cannot establish HOLDS.

Direct raw numeric transaction nonces must be nonnegative safe integers before comparison with the saved exact nonce; string nonces compare exactly. Every direct parent-to-child receipt edge must have nondecreasing finalized height, and the before balance must precede every supplied finalized execution. Same-block execution is allowed. Reused direct block hashes must agree on height and raw header facts across all attempt references and balance references; contradictory evidence remains INCONCLUSIVE with `CONFLICTING_BLOCK_REFERENCE`.

`evaluateTargetEvidence(target, approval, context?)` dispatches unsafe/guarded targets to the fixture oracle. Its optional `ScenarioEvaluationContext` contains `kind` and an optional `{ target, approval }` legitimate control. Supported fixture kinds are `fixture-legitimate`, `fixture-expired`, `recipient-substitution`, `lost-response-retry` and `concurrent-duplicates`. Validation derives context after every shape check, finding exactly one matching legitimate fixture target by account and target kind. It evaluates that control from raw evidence afresh; a supplied HOLDS flag is insufficient. Direct evaluation ignores this fixture context.

Fixture proof additionally checks complete receipt bodies and outcomes, function-call args/identity, native Transfer credit to canonical and alternate dedicated accounts, matching successful private `on_transfer` dependencies and attempt IDs, raw `get_config`/pre/post `get_approval` bytes, exact U128/U64 fields, finalized block timestamps and snapshot order. Policy rejections require the expected explicit contract panic and zero receipt/balance credit. Retry/concurrency require one completed approved credit plus a guarded policy rejection, or two distinct unsafe successful transfers. Nonce rejection, missing callback and unexpected failures remain INCONCLUSIVE. Pending is never automatically unlocked. The retry runner separately proves the first exact credit before preparing its intentionally fresh-nonce duplicate; intermediate raw balance queries remain in `rpcEvidence` and approval views in `stateSnapshots`.

Every parent-to-child receipt edge and native-transfer-to-dependent-callback execution must have nondecreasing finalized height and timestamp. Same-block execution is allowed when its facts agree. Reused block hashes must have consistent heights and complete header facts across attempt references, contract state and balance evidence, including height-only balance query references. Impossible order returns `RECEIPT_CHRONOLOGY`; conflicting block facts return `CONFLICTING_BLOCK_REFERENCE`. A native transfer must have exactly one output dependency to the fixture and its callback exactly one matching nonempty string input ID. Null, empty, nonstring, extra or malformed dependency entries remain INCONCLUSIVE with `MISSING_CALLBACK`.

In both direct and fixture evidence, receipt outcomes must use identifiers distinct from the signed transaction hash. Fixture receipt bodies must also satisfy this identity rule. An alias returns INCONCLUSIVE with `INCONSISTENT_RECEIPT_IDENTITY` before receipt-graph or execution-position checks.

`validateRunReport(input)` returns `{ valid: true, errors: [], report }` or `{ valid: false, errors: string[] }`. It checks the public JSON shape, network, schema, exact amount strings, provenance, required evidence fields and derived verdicts. `assertRunReport` returns the typed report or throws validation errors. Validation recalculates stored verdict status, summary, amounts, reason codes and transaction hashes. Secret-bearing fields are forbidden. Public signature exceptions are restricted to recognized transaction/block results or envelopes and declared report evidence slots: transaction signatures, block header signatures, chunk signatures and validator approval signatures in `header.approvals`. Arbitrary `extension.signature` fields do not qualify. Known supplied secret strings are always redacted even in these public slots. Validation does not authenticate an imported report, an RPC operator, or account isolation.

The JSON scan has finite limits of 1,000,000 nodes, depth 60, 2,000,000 characters per string and 100 reported errors. The node budget covers ten targets with retained raw FINAL/status/block copies, multi-shard chunk metadata and validator approvals; the original direct-only 100,000-node budget could interrupt a complete suite checkpoint. The dashboard also caps uploaded files at 20 MiB. These bounds limit imports; they do not make missing or inconsistent financial evidence conclusive.

Report consumers can display raw public signatures, transaction hashes, signer public keys and outcomes. They must retain provenance labels and use verdict text as well as color. Do not ship an offline fixture as recorded execution.
